## 진행 원칙

- **순서 준수**: 기반(설정) → 공통 모듈 → 핵심 기능 → 부가 기능 → 품질 향상 순으로 진행한다. 앞 Phase의 완료 기준을 충족하기 전에 다음 Phase로 넘어가지 않는다.
- **구현 전 확인**: 모든 구현 전에 `node_modules/next/dist/docs/`의 Next.js 16 가이드를 먼저 확인한다 (`AGENTS.md` 지침).
- **타입 규칙**: `any` 타입 사용 금지.
- **반응형 규칙**: 모든 화면은 360px 이상에서 가로 스크롤 없이 동작해야 한다. Tailwind 브레이크포인트로 구현한다.
- **보안 규칙**: Notion API 키(`NOTION_API_KEY`)와 데이터베이스 ID는 환경변수로만 관리하고 저장소에 커밋하지 않는다. 데이터 조회는 서버에서만 수행한다.
- **진행 관리**: 각 작업 완료 시 체크박스를 체크하고, Phase 상태 표를 갱신한다.

## Phase 1: 프로젝트 초기 설정

**예상 기간**: 1 ~ 2일
**PRD 연관**: §4 기술 스택, §7 아키텍처, §10 1단계, §10 2단계

### 목표
Notion API에 연결할 수 있는 개발 환경과 기본 레이아웃 뼈대를 갖춘다.

### 작업 목록
- [ ] 스타터킷 상태 점검: 기존 `app/`, `components/layout/`, `config/site.ts`, `components/ui/`(shadcn) 구조 확인
- [ ] `config/site.ts`를 블로그 정보(블로그 이름, 설명, 기본 URL)로 수정
- [ ] `@notionhq/client` 패키지 설치
- [ ] `.env.local`에 `NOTION_API_KEY`, `NOTION_DATABASE_ID` 설정
- [ ] `.gitignore`에 `.env*.local`이 포함되어 있는지 확인
- [ ] Notion 데이터베이스 생성 및 PRD §5 속성 추가 (Title, Category, Tags, Published, Status)
- [ ] Notion Integration 생성 후 데이터베이스에 연결(공유)
- [ ] 테스트용 글을 `발행됨`과 `초안`으로 각각 1개 이상 작성
- [ ] Notion API 클라이언트 초기화 모듈 작성 (`lib/notion.ts`)
- [ ] 공통 레이아웃(헤더, 푸터) 뼈대를 블로그용으로 정리

### 이유
견고한 기반(환경변수, API 연결, 레이아웃 뼈대) 없이는 이후 기능 개발이 어렵다. 특히 API 키 관리 방식은 처음에 정해야 이후 실수를 막을 수 있다.

### 완료 기준
- [ ] `npm run build`와 `npm run lint`가 오류 없이 통과한다.
- [ ] `lib/notion.ts`로 Notion 데이터베이스 조회가 성공한다 (테스트 글 응답 확인).
- [ ] API 키가 클라이언트 번들이나 저장소에 노출되지 않는다.
- [ ] 테스트 글이 `발행됨`/`초안` 상태로 준비되어 있다.

## Phase 2: 공통 모듈 개발

**예상 기간**: 2 ~ 3일
**PRD 연관**: §5 데이터 구조, §5.1 데이터 규칙, §6.1 공통 레이아웃, F1, F2

### 목표
모든 기능에서 재사용할 데이터 함수, 타입, 공통 컴포넌트를 먼저 만들어 중복을 막는다.

### 작업 목록
- [ ] 공통 타입 정의: `Post`, `Category` (Notion 속성 매핑 포함, `any` 없이 작성)
- [ ] `fetchPages` 구현
  - Status = `발행됨` 필터
  - Published 내림차순 정렬, 값이 없으면 맨 뒤
  - Category가 비어 있어도 목록에는 포함
- [ ] `fetchPageContent` 구현 (페이지 본문 블록 조회)
- [ ] 카테고리 목록 조회 함수 구현 (Category select 선택지 기반)
- [ ] `Header` 컴포넌트: 블로그 이름, 카테고리 메뉴, 모바일 접힘 메뉴
- [ ] `Footer` 컴포넌트: 간단한 저작 정보
- [ ] `Card` 컴포넌트(`PostCard`): 제목, 카테고리, 태그, 발행일 표시
- [ ] 오류 처리 공통화: Notion API 실패 시 오류 안내 상태 반환 + 서버 로그 기록

### 이유
목록, 상세, 카테고리 페이지 모두 같은 데이터 함수와 타입, 카드 컴포넌트를 사용한다. 먼저 공통 모듈을 만들어 두면 페이지마다 같은 코드를 반복 작성하지 않는다.

### 완료 기준
- [ ] `fetchPages` 결과에 `초안` 글이 포함되지 않는다 (테스트 글로 확인).
- [ ] Published 정렬이 최신순이며, 값이 없는 글은 마지막에 위치한다.
- [ ] 타입 정의에 `any`가 없고 `npm run lint`가 통과한다.
- [ ] `Header`, `Footer`, `PostCard`가 360px 화면에서 줄바꿈과 가로 스크롤 없이 표시된다.
- [ ] API 실패 시 빈 화면 대신 오류 안내가 표시된다.

## Phase 3: 핵심 기능 개발

**예상 기간**: 3 ~ 4일
**PRD 연관**: F1 글 목록, F2 글 상세, §6 화면 구성, §7 ISR, §11 이미지 리스크

### 목표
블로그의 가장 기본이 되는 목록 페이지와 상세 페이지를 완성한다.

### 작업 목록
- [ ] 홈 페이지(`/`) 구현: 발행된 글을 카드형 목록으로 렌더링
- [ ] 글 상세 페이지(`/posts/[slug]`) 구현
  - 제목, 카테고리, 태그, 발행일, 본문 표시
  - 존재하지 않거나 `초안`인 글은 404 처리
- [ ] Notion 블록 → HTML 렌더러 구현
  - 지원 블록: 제목, 문단, 목록(순서/비순서), 인용, 이미지, 코드
  - 미지원 블록은 "지원하지 않는 콘텐츠" 안내 문구로 표시
- [ ] 이미지 URL 만료 대응 방식 적용
  - 방안 A: 재검증 주기 내 갱신, 또는
  - 방안 B: 서버에서 내려받아 저장
  - 구현 전 방식 선택 후 이 문서에 결정 기록
- [ ] ISR 재검증 주기(`revalidate`) 값 확정 및 적용
- [ ] 이미지에 대체 텍스트(alt) 제공

### 이유
블로그의 본질인 "목록 → 글 읽기" 흐름을 완성하는 단계다. 이 기능이 동작해야 이후의 카테고리 필터나 SEO 작업이 의미를 가진다.

### 완료 기준
- [ ] Notion에서 `발행됨`으로 바꾼 글이 재검증 주기 안에 홈 목록에 나타난다. (PRD F1)
- [ ] `초안` 글은 목록과 상세 어디에서도 노출되지 않는다. (PRD F1)
- [ ] 없는 글 주소 또는 `초안` 글 주소 접근 시 404 페이지가 표시된다. (PRD F2)
- [ ] 지원 블록이 정상 렌더링되고, 미지원 블록은 안내 문구로 대체된다.
- [ ] 이미지가 Notion URL 만료 후에도 깨지지 않는다.

## Phase 4: 추가 기능 개발

**예상 기간**: 2 ~ 3일
**PRD 연관**: F3 카테고리 필터링, F4 검색(후속 단계), §8 SEO, §11 카테고리 리스크

### 목표
핵심 기능 위에 카테고리 탐색과 검색 가능성, 검색엔진 노출을 더한다.

### 작업 목록
- [ ] 카테고리 페이지(`/category/[name]`) 구현
  - 카테고리 이름을 slug로 변환하여 URL에 사용
  - 한글 및 특수문자 URL 인코딩 처리
  - 해당 카테고리이면서 `발행됨`인 글만 표시
  - Category가 비어 있는 글은 제외
- [ ] 헤더 카테고리 메뉴에 카테고리 목록 연결 (Notion 선택지 동적 조회)
- [ ] 검색 기능 (PRD F4, 후속 단계)
  - 제목과 태그 기준 키워드 검색
  - Notion API 조회 결과를 서버에서 필터링하는 방식으로 구현
- [ ] SEO 메타 정보 설정
  - 페이지별 `title`, `description`
  - Open Graph 메타 정보 (`generateMetadata` 활용)

### 이유
핵심 기능이 안정된 뒤에 부가 기능을 추가한다. 카테고리 필터는 PRD에서 MVP 포함 기능이며, 검색은 PRD §9에서 MVP 제외로 분류된 후속 단계다.

### 완료 기준
- [ ] 카테고리 페이지에 해당 카테고리의 `발행됨` 글만 나온다. (PRD F3)
- [ ] 한글 카테고리 URL이 올바르게 인코딩되어 동작한다. (PRD F3)
- [ ] 홈에서 카테고리 페이지까지 2회 이내 클릭으로 진입할 수 있다. (PRD §2)
- [ ] 검색 결과가 제목과 태그 기준으로 정확히 나오며 `초안` 글은 포함되지 않는다.
- [ ] 주요 페이지에 `title`, `description`, Open Graph 메타 정보가 있다.

## Phase 5: 최적화 및 배포

**예상 기간**: 1 ~ 2일
**PRD 연관**: §2 성공 지표, §8 비기능 요구사항, F5 반응형, §10 5단계

### 목표
기능이 완성된 상태에서 성능, 반응형, 접근성을 점검하고 Vercel에 배포한다.

### 작업 목록
- [ ] 성능 최적화
  - Notion API 호출 횟수 점검 및 캐시 적용 확인
  - 이미지 최적화 (`next/image` 사용 여부 점검)
- [ ] 반응형 디자인 점검
  - 360px ~ 데스크톱 전 구간 확인
  - 가로 스크롤 발생 여부 확인
  - 터치 대상 크기 확인
- [ ] 접근성 점검
  - 이미지 대체 텍스트, 색 대비, 키보드 탐색
- [ ] Vercel 프로젝트 생성 및 배포
- [ ] Vercel 환경변수 설정 (`NOTION_API_KEY`, `NOTION_DATABASE_ID`)
- [ ] 배포 환경에서 재검증 주기 동작 확인

### 이유
기능이 완성된 뒤 품질을 끌어올린다. 배포는 마지막에 하되, 환경변수 설정 방식은 Phase 1에서 이미 정해 두었으므로 배포 시 혼선이 없다.

### 완료 기준
- [ ] 360px 이상 모든 화면에서 가로 스크롤이 없다. (PRD §8)
- [ ] Vercel 배포 URL에서 모든 화면이 정상 동작한다.
- [ ] Notion에서 `발행됨`으로 바꾼 글이 재검증 주기 안에 배포 사이트에 반영된다. (PRD §2 성공 지표)
- [ ] API 키가 배포 결과물에 노출되지 않는다.
